# Paper2Run 平板远程端设计

日期：2026-11-05
状态：待审批

## 1. 意图

Paper2Run 的全部服务（FastAPI、沙箱、模型调用、SQLite）继续只运行在电脑上。新增一个 Android 平板 App，让用户在**跨网络的远程环境**（平板在 4G/外部 Wi-Fi，电脑在家或实验室）下，看到并操作与电脑端完全相同的页面。连接优先 P2P 打洞直连，失败时经用户自有服务器中继。两端通过配对码完成配对，之后自动重连。

## 2. 目标 / 非目标 / 反目标

目标
- 平板端功能与电脑端一致：上传论文、六步引导、Session 工作台、启动/取消运行、报告查看与导出、设置。
- 跨 NAT 远程可用：直连优先，自动降级到中继，用户无需配置端口转发或 VPN。
- 配对码一次配对，之后长期自动重连；电脑端可查看、撤销已配对设备。
- 端到端加密：中继服务器只转发密文，无法读取或篡改内容。

非目标
- 不把计算迁移到平板或服务器；平板不执行任何实验。
- 本期不把隧道进程打包进 Electron 安装包。
- 不做 iOS 版本，不做手机竖屏专门适配（平板横/竖屏可用即可）。
- 不重写前端页面，不为平板单独开 API。
- 不做多人协作/并发锁；两端同时操作时以后端状态为准，靠现有轮询收敛。

反目标（技术上能跑但算失败）
- FastAPI 改为监听 `0.0.0.0` 或任何非 loopback 地址。
- 拿到配对码之外的任何人（包括中继服务器运营方）能访问电脑上的服务。
- 平板端是一个功能残缺、和电脑端行为不一致的"另一个产品"。
- 声称"已打洞成功"而实际走的是中继——连接状态必须如实显示（与项目"程序判定、如实报告"的原则一致）。

## 3. 现状与约束

- 前端：React SPA（`apps/web`），实时性靠 3–5 秒 `refetchInterval` 轮询；仅两条 SSE 流：`services/api/p2r_api/routes/runs.py:625`、`services/api/p2r_api/routes/sessions.py:187`。
- 后端：只监听 `127.0.0.1`（`scripts/launch.py`、`apps/desktop/main.cjs` 均如此），端口从 8010 起自动选取。
- 安全检查（已核对代码）：两个启动器都用 `create_demo_app`，它设 `development_auth=True`、固定 `demo-user`，**不做 cookie/会话认证**（`services/api/p2r_api/dependencies.py:95-102`）。`allowed_origin` 写死为 `http://127.0.0.1:8000`（`services/api/p2r_api/main.py:170`），而实际端口是 8010 起；`autonomous.py:81` 的写检查仍严格比对这个值——这是桌面端已有的 bug。Electron 后端另有 `host_guard`，只放行 `Host`/`Origin` 等于真实 `127.0.0.1:<端口>` 的请求（`apps/desktop/backend/serve.py:84`）。
- 结论：后端本身没有用户认证，**隧道边车是远程访问唯一的门**。
- 桌面集成：`window.p2rDesktop` 仅 Electron 有，浏览器中会降级（`apps/web/src/desktop.ts`）——平板 WebView 中同样降级。
- 两种启动方式都要支持：`scripts/launch.py`（一键启动）与 Electron 桌面版（`apps/desktop`）。
- 分层约束 `tests/unit/test_architecture.py` 与三文件源根同步 `tests/unit/phase01/test_packaging.py` 必须保持通过；新增 Python 包需同时登记。
- 测试平板：adb 序列号 `HA2KPCA4`，当前状态 `unauthorized`，需用户在平板上授权 USB 调试。系统版本、ABI 未知。

## 4. 方案比较（已选 A）

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A. iroh（已选）** | Rust QUIC 库，Tailscale 式设计：公钥即身份，内置打洞，失败自动走 relay；`iroh-relay` 可自建 | 组件最少，配对=交换公钥，天然 E2E 加密；项目较年轻，Android 端需 Rust 交叉编译（主要风险） |
| B. WebRTC DataChannel | STUN/TURN + 自写信令 | 最成熟；但 ICE/信令/TURN 三件套需自拼，且要在 DataChannel 上自行实现 HTTP 多路复用和 SSE |
| C. tsnet + Headscale + DERP | 嵌入 Tailscale | 打洞最久经考验；为暴露一个 HTTP 服务引入整套组网系统，偏重；配对码需映射到 preauth key |

未纳入：ZeroTier libzt（BSL 许可、偏重）、libp2p（复杂度过高）、frp 类工具（只有中继）。

选择 A 的理由：最贴近用户提到的 Tailscale 思路，用户服务器上只需部署一个程序，配对与加密模型最简单。

## 5. 总体架构

```
┌──────────── 平板 (Android App) ────────────┐        ┌──────── 电脑 ────────┐
│ WebView ──HTTP──> 127.0.0.1:<本地端口>      │        │                      │
│                   本地反向代理 (Rust, iroh) ─┼─QUIC──>│ p2r-tunnel 边车进程   │
└─────────────────────────────────────────────┘ 直连或 │   └─HTTP─> 127.0.0.1:  │
                         │                      经中继  │        <后端端口>     │
                         ▼                             │   FastAPI (不变)      │
              用户服务器：iroh-relay + 配对会合服务       └──────────────────────┘
```

关键思路：**隧道传的是原样 HTTP**。平板 WebView 访问本机代理，代理把请求经 iroh 发给电脑上的边车，边车再转发到 `127.0.0.1:<后端端口>`。后端看到的是一个普通的 loopback 请求，前端代码基本不改。

### 5.1 电脑端：`p2r-tunnel` 边车
- Rust 二进制，持有电脑的长期 iroh 密钥与已配对设备列表，存于**用户级目录**（如 `~/.paper2run/remote/`，Windows 为 `%APPDATA%\Paper2Run\remote\`，权限 0600），而非各启动器自己的 demo 目录，这样 `launch.py` 和 Electron 共享同一个电脑身份，平板配对一次两种启动方式都能连。（我的决定。）
- 只接受**已配对设备公钥**的连接；未知公钥直接断开（配对流程除外，见 §6）。
- 把每个 QUIC 流映射为一次 HTTP 请求/响应，转发到后端；需支持流式响应（SSE）和大文件上传。
- 由 `scripts/launch.py` 与 Electron `main.cjs` 在后端健康检查通过后启动，随后端一起退出；后端端口作为参数传入。
- 提供一个仅 loopback 的控制接口（带随机 token），供 FastAPI 调用：生成配对码、列出设备、撤销设备、查询连接状态（直连/中继/离线）。

### 5.2 后端与前端改动（最小）
- FastAPI 新增路由（如 `/api/v1/remote-devices`）代理到边车控制接口；需登记分层。
- 设置页新增"平板远程"区块：生成并显示配对码（附二维码可选）、已配对设备列表（名称、最近在线、当前连接方式）、撤销按钮。
- **Origin/Host 处理**：由电脑端边车（它知道后端真实端口）在转发前把 `Host` 改写为 `127.0.0.1:<后端端口>`，`Origin` 存在时改写为 `http://127.0.0.1:<后端端口>`，去掉 `Sec-Fetch-Site`。这样能通过 Electron 的 `host_guard`，不放宽后端检查。（我的决定：放在电脑端而非平板端，因为只有电脑端知道端口。）
- **顺带修复**：`create_demo_app` 的 `allowed_origin` 改为由实际监听端口决定，修好 `autonomous.py` 写检查与真实端口不一致的已有 bug——否则电脑端和平板端的 autonomous 写操作都无法达到"功能一致"。（我的决定。）
- Session/cookie：demo 模式下无会话认证，平板 WebView 与电脑浏览器看到的是同一个 `demo-user`。

### 5.3 Android App（`apps/android`）
- Kotlin，单 Activity + WebView；Rust 隧道库通过 uniffi/JNI 嵌入，在平板本机 loopback 起代理。
- 首次启动：输入配对码 → 配对成功后保存设备密钥与电脑公钥（Android Keystore 加密存储）→ 加载页面。
- 之后启动自动重连；断线时显示"电脑离线 / 正在重连 / 直连 / 经中继"状态条。
- WebView 需补齐：文件选择（`onShowFileChooser`，用于上传 PDF）、下载（`DownloadListener`，用于导出）。
- 通过 adb 安装调试版 APK；不上架应用商店。

### 5.4 用户服务器
- 华为云 `60.204.202.153`，可用端口 **12234**，无域名、无 TLS 证书。2026-11-05 探测：TCP 12234 返回 connection refused（主机和安全组可达，尚无服务监听）；UDP 12234 是否放行未能确认；SSH 22 可达。
- 只有一个端口，所以服务器端做成**一个进程**：基于 `iroh-relay` 的服务端库，在 TCP 12234 上以纯 HTTP 提供中继，同一进程挂配对会合接口与地址发布接口；若 UDP 12234 放行，再在其上提供 QUIC 地址发现（打洞辅助）。
- 中继自身不加 TLS 可以接受：中继只转发两端之间已经 QUIC/TLS 端到端加密的数据，看不到内容；配对安全靠 PAKE，不靠中继的证书。
- **完全不依赖 n0 公共服务**（国内 4G 下可能不可达）：两端只配置这一台服务器。电脑上线时把自己的当前地址发布到该服务器（用电脑私钥签名，平板用已保存的电脑公钥验证），平板重连时从这里取。验证阶段也直接用这台服务器。（我的决定，基于服务器在国内且平板走国内网络。）
- 配对会合接口只做"配对码哈希 → 电脑节点地址"的短时映射，**不参与认证**。

## 6. 配对与安全模型

1. 用户在电脑设置页点击"配对平板"，边车生成一次性配对码（建议 8 位，易输入，有效期 5 分钟，单次使用），并在会合服务登记"码的哈希 → 电脑节点地址"。
2. 平板输入配对码，从会合服务取到电脑节点地址，发起 iroh 连接。
3. 双方在该连接上用配对码跑 **PAKE（如 SPAKE2）** 互相证明知道同一个码，再交换并确认长期公钥。会合服务或中继即使作恶，也无法冒充任何一端（它们不知道码，猜测次数受单次使用和限速约束）。
4. 电脑把平板公钥加入允许列表，平板保存电脑公钥。此后每次连接都靠公钥认证，配对码失效。
5. 撤销：电脑端从允许列表移除，立即断开该设备的现有连接。
6. 后端依然只监听 loopback；所有远程流量都必须经过边车的公钥校验。

## 7. 已定决策

- 平板端功能与电脑端完全一致（用户决定）。
- 场景以跨网络远程访问为主（用户决定）。
- 采用方案 A：iroh（用户决定）。
- 打洞失败时由用户服务器做中继：华为云 `60.204.202.153:12234`（用户决定）。
- 配对和设备管理只能在电脑上操作（用户决定）。边车对远程连接拦截配对/设备管理接口（`/api/v1/remote-devices` 下的写操作）；平板设置页里这一块显示为只读。模型、SSH 等其它设置平板可改，与"功能一致"保持一致。（后半句是我的决定。）
- 打包进 Electron 安装包稍后再说（用户决定）；本期只需从源码运行（`launch.py` 和 `pnpm dev`/`electron .`）可用。

## 8. 交给实现者决定

- 隧道协议细节：HTTP/1.1 原样转发还是 h3/自定义帧；只要满足 SSE 流式、大文件上传、并发请求即可。
- Rust 项目结构（如 `apps/tunnel` 下 workspace：core / desktop 二进制 / android 绑定 / relay 侧会合服务）。
- 新增 FastAPI 路由所在包与分层位置（需让 `test_architecture.py` 通过）。
- Android minSdk、目标 ABI（以授权后的实际平板为准）。
- 配对码字符集与二维码是否提供。

## 9. 风险与第一步

- **主要风险**：iroh 在 Android 上的交叉编译与打洞表现；对称 NAT 下必然走中继，速度取决于服务器带宽（影响 PDF 上传）。
- **4G 下大概率走中继**：运营商 NAT 常常打不通。只要状态条如实显示，纯中继也算可接受（用户已把中继定为兜底）。（我的决定。）
- **spike 失败的处理**：如果 iroh 在平板上编译不了或跑不稳，停下来带着结果回到方案选择，不自行切换到 B/C。（我的决定。）
- **第一步（spike）**：电脑与平板经 iroh 打通一个 HTTP 请求——先用公共 relay，再换用户服务器；同时验证一次蜂窝网络下的打洞结果和一次 SSE 流。spike 结论回到设计里再进入正式实现。

## 10. 验收标准

- 平板在 4G 下、电脑在家庭 NAT 后，能完成一次完整六步流程（上传 → 抽取 → 生成 → 运行 → 评估 → 导出），SSE 日志实时滚动。
- 状态条如实显示直连或中继；强制屏蔽 UDP 直连时能自动降级到中继并继续工作。
- 未配对设备、过期/已用配对码、已撤销设备都无法访问任何接口。
- 已配对平板无法生成配对码或撤销设备（接口被边车拦截，界面只读）。
- 全程不访问任何 n0 公共服务（抓包或关闭默认 discovery 验证）。
- 后端监听地址仍为 `127.0.0.1`；`test_architecture.py`、`test_packaging.py` 通过。
