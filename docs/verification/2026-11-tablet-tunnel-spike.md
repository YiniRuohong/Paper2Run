# 平板隧道可行性实测（Plan 1 / Task 6）

日期：2026-11-05
设计：`docs/superpowers/specs/2026-11-05-tablet-remote-design.md`
计划：`docs/superpowers/plans/2026-11-05-tablet-tunnel-foundation.md`

本文只记录实际测到的结果，没有测的项目会写明"未测"。

## 结论

- **iroh 方案可行，可以进入 Plan 2（配对）和 Plan 3（Android App）。** 隧道在真平板上跑通了两种网络环境，自建中继工作正常，切换网络后能自动恢复。
- **同一 Wi-Fi 下打洞成功**：连接先经中继建立，几秒内升级为直连。
- **跨网络（平板用手机热点）时没有打洞成功，全程走中继**，但功能完整：页面正常显示，真实论文上传后与原文件逐字节一致。
- **瓶颈在中继带宽**：华为云出口约 3.3 Mbit/s。走中继时上传约 0.2 MB/s，64 MB 的论文约需 5 分钟；浏览页面、轮询进度不受影响。

## 环境

| 项 | 值 |
|---|---|
| 电脑 | macOS（Darwin 25.6.0），家庭网络，公网出口 `115.216.32.166`（仅 IPv4） |
| 平板 | Lenovo TB522FU，Android 16（SDK 36），arm64-v8a，adb `HA2KPCA4` |
| 平板浏览器 | 系统自带 `com.zui.browser`（未装 Chrome） |
| 中继 | iroh-relay 1.4.1，`https://60.204.202.153:12234`（TCP：HTTPS 中继；UDP：QUIC 地址发现），自签 CA 由客户端钉住 |
| 隧道 | `p2r-tunnel`（`apps/tunnel`），电脑端 `serve`、平板端 `connect`（以 adb 命令行运行，尚无 App） |
| 后端 | `create_demo_app`，`127.0.0.1:8010`，数据目录 `.p2r-guided-verification/runtime` |

测量方法：
- 延迟：Mac 经 `adb forward` 访问平板本机隧道端口，连续 20 次 `GET /healthz`。这条路径多了一段 USB，但这段 USB 的耗时可以忽略。
- 吞吐：在平板上用 `toybox nc` 直接从本机隧道端口发 POST，打到电脑上一个只做 SHA-256 校验的接收端，不经过 USB。用接收端而不是真实上传接口，是为了避免造出大量论文记录、触发解析。真实上传另外单独测了一次（见场景 B）。

## 场景 A：同一 Wi-Fi（10.1.1.0/24）

| 指标 | 结果 |
|---|---|
| 路径 | 先 `relay`（rtt 370 ms），约 0.1 s 后升级为 `direct`（rtt 36 ms），两端日志一致 |
| `/healthz` 经隧道 | 平均 112.6 ms，p50 108.8 ms，最大 247 ms（n=20） |
| 对照：平板直接 ping 电脑 | 平均 134.6 ms（这个 Wi-Fi 本身延迟就高） |
| 20 MB 上传（直连） | 4960–6081 ms，3.3–4.0 MB/s，3 次哈希全部一致 |
| 对照：裸 TCP 平板→电脑 | 1.9–4.1 MB/s |
| 20 MB 上传（`--relay-only`） | 89.9 s，0.22 MB/s，哈希一致 |
| 页面 | `/lab` 正常显示，数据经隧道定时刷新（`assets/2026-11-tablet-tunnel/A-lab.jpg`） |

## 场景 B：跨网络（平板连手机热点"Redmi K40 Gaming"，联通移动网络）

| 指标 | 结果 |
|---|---|
| 切换网络 | 10:33:32 Wi-Fi 断开，旧连接超时；0.2 s 后自动经中继重连，进程无需重启，页面不中断 |
| 路径 | 只有 `relay`：原连接观察 > 90 s、新建连接观察 > 60 s，都没有升级为直连 |
| 公网地址发现 | 两端都成功：电脑 `115.216.32.166:2054`，平板 `211.90.236.202:9607`；`udp_v4: true`，`udp_v6: false` |
| `/healthz` 经隧道 | 平均 190 ms，p50 190 ms，最大 426 ms（n=20） |
| 对照：平板直接 ping 中继 | 平均 196 ms |
| 5 MB 上传（中继） | 20.4–26.5 s，0.19–0.25 MB/s，哈希一致 |
| 页面 | `/lab` 正常显示（`B-lab.jpg`） |
| 真实上传 | 用户在平板浏览器里选择 `p2r-sample-paper.pdf`（526,197 B，项目 e2e 测试用论文）上传：`POST .../papers` → 202；后端存的 sha256 `2bd75fee…2cff` 与原文件一致；识别为 48 页；页面进入第 2 步（`B-after-upload.jpg`） |

**为什么没有打洞成功**（推断，未能直接证实）：平板在手机热点 NAT 后面，外面还有一层运营商级 NAT。这类 NAT 通常对每个目标地址分配不同的外部端口，所以中继看到的端口和平板发往电脑时用的端口不同，打洞失败。只有一台中继时，iroh 无法判断 NAT 是否是这种类型（`mapping_varies_by_dest_ipv4: None`）。IPv6 这条路也走不通：电脑没有 IPv6，中继也只有 IPv4（用的是 IP 地址，没有 AAAA 记录）。

## 场景 C：跨网络 + 强制只走中继

没有单独测：场景 B 本来就自动退到了中继，所以 B 实际上就是 C。强制只走中继的吞吐见场景 A（0.22 MB/s），与场景 B 一致。

## 过程中发现的问题

1. **一把密钥同一时间只能有一个隧道进程。** 两个进程用同一把密钥连到同一个中继时会互相顶掉。最早几次中继测试失败就是这个原因，那些数字已作废。Plan 3 的 Android App 必须保证同一把密钥只运行一个隧道进程。
2. **主目录的前端构建产物带了 `/Paper2Run/` 子路径。** `apps/web/dist`（2026-11-05 17:25 构建，被 git 忽略）引用 `/Paper2Run/assets/...`，但后端把静态文件挂在 `/assets/...`，所以 JS 请求拿到的是 HTML，页面空白。直接在电脑上访问也一样，和隧道无关。`vite.config.ts` 里没有设置 `base`，来源不明。本次测试用的是另外构建的正常版本（`/tmp/p2r-web-dist`），主目录的 `dist` 没有改动。
3. **uvicorn 会丢弃半关闭的连接，不返回响应。** 直接访问和经隧道都一样。浏览器不会半关闭连接，所以不影响使用，只影响 `nc` 这类测试脚本。
4. **"实时"其实是轮询。** 应用里的两个 SSE 接口是一次性返回已存的事件就结束，前端没有用 EventSource，页面每 3 秒轮询一次。经隧道轮询正常；流式转发由自动测试 `sse_chunks_arrive_before_stream_ends` 覆盖。
5. **第一次创建项目返回 403 是应用自己的设计**（`apps/web/src/features/guided/realflow.ts:144`）：demo 用户在第一次初始化时才创建。初始化之后，直接访问和经隧道都返回 200。

## 对后续计划的建议

- **Plan 2**：
  - 撤销设备必须断开它当前的连接（已实现：边车在每个请求流上重新检查允许列表）。设备管理接口替换允许列表文件时，要保持这一点。
  - Host/Origin 必须先校验是本机再改写（已实现，见设计文档 §5.2）。
  - 中继现在对所有人开放（`access = everyone`），应该改成只允许已配对设备的公钥（iroh-relay 支持 allowlist 模式）；
  - 配对码交换可以复用同一个 12234 端口。
- **Plan 3**：
  - App 内同一把密钥只运行一个隧道进程；
  - 状态条显示 `direct` / `relay`（数据来自 `paths::selected`）；
  - 走中继时，上传大文件前提示预计耗时。
- **中继带宽**：如果手机网络下的上传速度重要，需要调高华为云的公网带宽。按现在的带宽，跨网络时基本都走中继。

## 未测

- 平板在 Wi-Fi、电脑在另一个网络（比如电脑也在 NAT 后面的其他网络）的组合。
- 64 MB 满额上传经中继的实际耗时（按 0.2 MB/s 推算约 5 分钟）。
- 长时间（数小时）稳定性、平板锁屏或进入后台后的行为（要等 Plan 3 有了 App 才能测）。
- 抽取及之后的步骤（需要选择 PDF 解析方式和模型服务，不属于隧道验证）。
